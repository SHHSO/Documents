ER Templates in F&O

Electronic Reporting — from zero to a working template-driven document. Every step verified.
What ER Actually Is
The one-sentence version
ER is F&O's built-in engine for generating outbound documents (invoices, reports, regulatory filings) and parsing inbound files (bank statements, e-invoices) — using a layered architecture of abstract data models, mappings to real F&O tables, format definitions, and Office templates.

Why it exists

Before ER, document generation in AX/F&O was done via SSRS reports or X++ code. Both required a developer for every format change. ER lets a functional consultant modify templates (Excel/Word) without writing code. Microsoft also uses it as the vehicle for country-specific regulatory formats (tax declarations, e-invoicing) delivered through Globalization Studio.

You've already hit the edges of this — those ER format warnings on Sepura and the Gripple Tax Calculation Service issue both trace back to ER configurations that weren't set up in Globalization Studio.

The Four-Layer Architecture

Layer 1 — Data Model (Configuration)

An abstract tree of fields and containers. Think of it as a contract: "this document needs an InvoiceHeader with fields Date, Number, CustomerName, and a child list of InvoiceLines each with Product, Qty, Amount." It knows nothing about F&O tables — it's purely logical.

You almost never build this from scratch. Microsoft provides standard data models (e.g. "Invoice model", "Payment model"). You derive from them.

Layer 2 — Model Mapping

This is where abstract meets concrete. The mapping says: "InvoiceHeader.CustomerName = CustTable.Name, InvoiceLines comes from CustInvoiceTrans." It's the equivalent of a SSRS dataset, but declarative rather than SQL.

Multiple mappings can exist for one data model — e.g. one for "real" F&O data, one for "sample" test data. The system picks the right one at runtime based on the Integration Point.

Layer 3 — Format

Defines the structure of the output file. For an Excel template, it says: "there is a sheet called 'Invoice', with a named range 'Header' and a repeating range 'Lines'." For XML/JSON formats (e-invoicing), it defines the element tree. The format binds to the data model (not to F&O tables directly).

Layer 4 — Template

The actual .xlsx or .docx file. In Excel, you use Named Ranges that the Format component references. In Word, you use Content Controls. This is the bit your functional consultants can edit without touching ER at all — swap the template file, keep the bindings.

The "Configuration" wrapper

All four layers are packaged as ER Configurations. Each configuration has a type: Data model, Model mapping, or Format. They have versions (Draft → Completed → Shared) and they sit in a Configuration Provider (your organisation) inside a Repository (either the Global repo managed by Microsoft, or a local one). The versioning model is similar to solution layering in CE — you derive/extend, you don't edit the base.

Key mental model: Think of it like CE solution layering. Microsoft publishes base configurations via the Global repository. You create a derived version under your own provider. Your derived version inherits all the bindings and structure — you only override what you need. Never edit a Microsoft-published configuration directly (you can't anyway, it'll be read-only).
Before You Touch Anything
These must be done once per environment. If they're already done, skip — but verify they are.
1
Create or verify your Configuration Provider
▸

A Configuration Provider is your organisation's identity in the ER framework. Every configuration you create or derive is owned by a provider.

Organization administration → Electronic reporting → Configuration providers

If HSO (or your org) already appears in the list, click it and verify the Internet address (just a URL identifier — e.g. https://www.hso.com). Then click Set active on the Action Pane.

If it doesn't exist: New → Name: your org, Internet address: your org URL → Save → Set active.

Verification: The provider tile at the top of the ER workspace (next step) shows your provider name. If it says "Litware" or "Microsoft" you haven't set your provider active.
First-attempt mistake: People skip this step, then wonder why they can't edit configurations. ER will let you browse Microsoft's configs but you can't create or derive anything without an active provider that belongs to you.
Provider exists and is set as Active
2
Connect to the Global Repository
▸
Organization administration → Electronic reporting → Reporting configurations

This opens the ER Workspace — the configuration tree. On the Action Pane, look for Repositories.

Click Repositories. You should see a row for "Global". If not, click Add → select Global → Save. Then click Open on the Global repository row.

This connects your environment to Microsoft's centrally-published configuration library (hosted in RCS — Regulatory Configuration Service, now folded into Globalization Studio). This is where all the standard data models, mappings, and formats live.

Verification: After clicking Open, you see a massive tree of configurations (hundreds). Filter by name to find something like "Invoice model" — if you see it with Microsoft as the provider, you're connected.
Gotcha: In some locked-down environments (especially Tier-1 dev boxes), the Global repo connection may fail with a LCS/RCS credential error. This means the environment isn't linked to LCS properly. You'll need the sysadmin to verify the LCS project linkage in System administration → Setup → Lifecycle Services parameters. This is an environment config issue, not an ER issue.
Global repository accessible, can browse Microsoft configurations
3
Import the base configurations you need
▸

Inside the Global repository, find the base Data Model and Format you want to extend. Example: if you're building a custom invoice, search for Invoice model.

Select the configuration → click Import. This brings it into your local environment. Repeat for the Model Mapping and any Format you plan to derive from.

Shortcut: When you import a Format, F&O will auto-import all parent dependencies (the Data Model and Model Mapping it depends on). So if you know the exact Format you want, just import that one and let the system pull the chain.
Version matters: Always import the latest completed version. The Global repo shows all versions; pick the one with the highest version number and status "Completed" or "Shared". Do NOT import Draft versions — they may be incomplete and you'll get binding errors downstream.
Verification: Close the repository. Back in the Configurations tree, you should now see the imported config(s) with Microsoft as the provider. Expand the tree — the Data Model should show child Model Mapping and Format nodes.
Base configurations imported into local environment
4
Understand the Globalization Studio link (context only)
▸

Since ~2023, Microsoft has been consolidating RCS and the Tax Calculation Service under Globalization Studio, accessible as a workspace in F&O. The ER configurations tree still works the old way, but new regulatory features (like the Tax Calculation feature that bit Gripple) are managed through Globalization Studio → Features.

For template work specifically, you stay in the classic ER workspace. Globalization Studio matters when you're activating country-specific features that reference ER formats — but the template creation workflow itself hasn't moved.

Naming confusion: Microsoft documentation freely mixes "ER", "GER" (legacy name: Generic Electronic Reporting), "RCS", "Globalization Studio", and "Globalization features". They all refer to parts of the same system. ER = the engine. RCS/Global repo = the delivery mechanism. Globalization Studio = the newer unified workspace. For template creation, just use the ER workspace.
Understand the relationship — no action needed
Creating a Custom ER Format with Template
This walks through the most common scenario: you have a Microsoft base format and you want to customise the output (layout, fields, branding) by creating a derived format with your own Excel/Word template.
Running example
We'll derive a custom Free Text Invoice format. This is the most common first ER project — it's well-documented, the base config is robust, and the result is immediately testable. Everything here applies identically to Sales Invoices, Packing Slips, Purchase Orders, etc.
1
Create a Derived Format configuration
▸
Organization administration → Electronic reporting → Reporting configurations

In the configuration tree, find and select the Microsoft-published format you want to customise. E.g. expand Invoice model → find Free text invoice (Excel).

With that format selected, click Create configuration on the Action Pane.

In the dialog, select: "Derive from Name: Free text invoice (Excel), Microsoft".

Give it a name: e.g. Free text invoice (Excel) - HSO Custom.

Description: whatever helps you. Click Create configuration.

The trap: If "Create configuration" only shows "New" (not "Derive from..."), you either haven't selected a Format-type configuration, or your active provider isn't set. Go back to Prerequisites step 1.
Verification: Your new config appears as a child node under the Microsoft one, with YOUR provider name, and version 1 Draft. The status "Draft" is critical — it means you can edit it.
Pro tip: The derived config inherits ALL bindings from the parent. This is the whole point — you get a fully working format immediately, then only change what you need. If you create from scratch ("New"), you have to build every binding manually, which is days of work vs minutes.
Derived format created with Draft status under my provider
2
Open the Format Designer
▸

With your new derived config selected, click Designer on the Action Pane (or click into the version row and then Designer).

This opens the Format Designer — the core ER authoring surface. You'll see:

  • Left pane — Format tree: The structural hierarchy of the output file. For Excel, this is Sheets → Named Ranges → Cells. For Word, it's Content Controls.
  • Right pane — Data model tree: The abstract data model this format is bound to. These are the fields available for binding.
  • Bottom pane — Binding details: Shows which data model field is bound to which format element.

Because you derived, the tree is already populated with all the parent's structure and bindings. Everything is greyed/inherited — you override specific elements.

Verification: You can see format elements in the left tree (e.g. "Report → Invoice → Header → InvoiceNumber"). If the tree is empty, you created a "New" format instead of deriving. Delete it and redo step 1.
Format Designer open with inherited structure visible
3
Export the current template
▸

Before editing, extract the existing template so you have a working baseline.

In the Format Designer, on the Format tab of the Action Pane, click Import/Export → Export to Excel (or the template attachment area — look for a paperclip icon or "Attachments" depending on your version).

Faster path: In the Format tree, select the root element (e.g. "Excel"). In the properties on the right, look for Template. There should be an attachment — click it to download the .xlsx/.docx. The exact UI for this has shifted between versions — in newer builds it's under Format → Template → Edit in the ribbon, which opens the template in a browser-based editor or gives you a download option.
Critical nuance: There are two things people confuse: the Format structure (the tree in the designer) and the Template file (the actual Excel/Word doc). The template is attached to the format. When you modify the template, you're changing the visual layout. When you modify the format tree, you're changing the data binding logic. Most customisations involve both.

Save this downloaded template somewhere safe. Open it in Excel. You'll see:

  • Named ranges (check Formulas → Name Manager in Excel) — these are the anchor points ER uses
  • Placeholder text or sample values in cells
  • The visual layout that will become your output document
Verification: Open the downloaded .xlsx in Excel. Go to Formulas → Name Manager. You should see named ranges like ReportHeader, InvoiceLine, etc. These correspond to the format tree elements.
Template exported, named ranges visible in Excel Name Manager
4
Modify the Excel template
▸

Now edit the template in Excel. Common changes:

  • Add your company logo — insert an image in the header area
  • Rearrange columns — move cells around within existing named ranges
  • Add new cells for new fields — if you want to expose a data model field not currently in the template
  • Change fonts, colours, formatting — purely visual, no ER impact
  • Add/rename named ranges — only if you need new repeating sections
The Named Range Rule: ER binds to named ranges, not cell addresses. If you add a new cell and want ER to populate it, you MUST either: (a) place it inside an existing named range, or (b) create a new named range for it and then add a matching element in the Format tree. If you just put a cell somewhere without a named range, ER won't touch it — it'll be static text.
Repeating ranges: For line items (invoice lines, etc.), the named range defines the "template row" that ER will repeat. If you break this named range (e.g. merge cells across it, extend it incorrectly), ER will either crash or produce garbled output. Always test with multi-line data.
Minimal viable change: For your first time, just change a font colour or add a static text label. Prove the round-trip works before doing anything ambitious.
Common first-attempt failure: Editing the template in LibreOffice or Google Sheets. Don't. ER templates must be edited in desktop Excel. Other editors can corrupt named range definitions or change the internal XML structure of the .xlsx in ways that break ER's parser. Use proper Excel.
Template modified in desktop Excel, saved as .xlsx
5
Upload the modified template
▸

Back in F&O, in the Format Designer, replace the template:

Select the root element in the format tree (e.g. "Excel"). In the Action Pane or right-click context menu, look for Format → Template → Import from Excel or the Attachments button. Upload your modified .xlsx.

Version mismatch: If you added/removed named ranges in Excel, the Format Designer will flag mismatches. New named ranges in the template → you'll see warnings about unbound ranges. Removed ranges → errors about missing template elements. Both are fine — you resolve them in the next step (binding). But if you see "Template structure cannot be matched", you likely corrupted the file structure — re-export and start the template edit again.

After upload, the format tree may update to reflect new named ranges. Inherited elements from the parent that are unchanged stay as-is.

Verification: The template attachment timestamp updates. If you added a new named range, you should see a corresponding new element (or warning) in the format tree.
Modified template uploaded, no structural errors
Binding — Connecting Template Cells to Data
This is where most people stall. The binding UI is powerful but unintuitive. Take it slow.
1
Understand the binding model
▸

Binding connects a format element (left tree — a cell in your template) to a data model node (right tree — an abstract field). The chain is:

Template Cell ← Format Element ← Data Model Node ← Model Mapping ← F&O Table.Field

When you derived the format, all existing bindings came with it. You only need to bind new elements (cells you added to the template).

Binding types you'll encounter

Simple binding: Format element → Data model field. E.g. Cell "InvoiceDate" → model.InvoiceHeader.Date.

Calculated field: Instead of binding to a model field, you write a formula using ER's expression language (similar to Excel formulas). E.g. FORMAT(model.InvoiceHeader.Date, "dd/MM/yyyy").

Sequence/List binding: A container element bound to a list in the data model. ER iterates it. This is how line items repeat.

2
Bind a new cell to an existing data model field
▸

In the Format Designer:

  1. Select the new format element in the left tree (the one created when you uploaded the template with a new named range/cell)
  2. In the right tree (Data model), expand to find the field you want
  3. Click Bind on the Action Pane (or drag the model field onto the format element — UI behaviour varies by version)
Can't find the field? The data model is abstract — it only exposes what Microsoft (or whoever built the model) put there. If the F&O field you want isn't in the data model tree, you have two options:
(a) Create a Calculated field in the Format that queries it via ER functions — this is limited to what ER functions support.
(b) Extend the Model Mapping — derive the model mapping config and add a new datasource/field that pulls from the F&O table you need. This is the deeper approach but it works for anything.
Verification: Select the format element. The bottom pane should show the binding — the data model path it's connected to. If it says "Not bound" or shows nothing, the binding didn't take.
New cell bound to data model field, binding visible in bottom pane
3
Write a calculated field / formula (if needed)
▸

If you need to transform data (format a date, concatenate strings, do math), use a calculated field.

Select the format element → instead of binding to the model tree, click Edit formula (or fx button) at the bottom of the binding pane.

This opens the Formula Designer. The expression language is ER-specific (not X++, not C#):

NeedER Expression
Format a dateDATETIMEFORMAT(model.Header.Date, "dd-MMM-yyyy")
Concatenate stringsCONCATENATE(model.Header.InvNum, " - ", model.Header.CustName)
Conditional valueIF(model.Header.Amount > 1000, "High", "Standard")
Sum of line amountsSUMIF(model.Lines, model.Lines.Amount, true)
Current date/timeSESSIONTODAY()
Built-in functions list: In the formula editor, the left panel shows all available functions grouped by category. Use the search. Microsoft's full ER function reference: search for "ER formula designer" in Learn docs — it's a long but complete reference.
Common failure: The formula editor validates on save. If it won't save, the syntax is wrong. The most frequent cause: wrong function name or wrong argument count. ER's function names are NOT the same as Excel's in many cases. TEXT() doesn't exist — use DATETIMEFORMAT() or NUMBERFORMAT().
Formula validates and saves without errors
4
Validate the format
▸

In the Format Designer, click Validate on the Action Pane. This checks:

  • All format elements are either bound or explicitly marked as "not bound" (suppressed)
  • Formula syntax is valid
  • Template structure matches format tree
  • No circular references
Warnings vs Errors: Warnings (yellow) are informational — the format will still run. You saw these on Sepura (shared model noise). Errors (red) are blocking — you can't complete the version until they're fixed. Read the error messages carefully — they're verbose but usually point to the exact element.
Verification: Validation returns 0 errors. Warnings are acceptable (note them, understand them, but they won't block you).
Validation passed (0 errors)
5
Complete the version
▸

Close the designer. Back in the Configurations tree, select your derived format. On the Action Pane, click Change status → Complete.

This moves the version from Draft to Completed. A Completed version is read-only but runnable. You must complete the version before it can be used in production.

During development: You can run a Draft version for testing — you don't have to complete it first. But in a production scenario, it must be Completed. Draft → test → fix → Draft again if needed (create new version) → Complete when ready.
Can't uncomplete: Once Completed, that version is locked. If you need to edit, you create a new version (it copies the completed one) which starts as Draft. The version numbering increments automatically.
Version status changed to Completed (or staying Draft for testing)
Testing Your Template
1
Assign the format to the document type
▸

Your format exists but F&O doesn't know to use it yet. You need to assign it as the active format for the relevant business document.

Organization administration → Electronic reporting → Electronic reporting destination (or: Document configuration)

The exact path depends on the document type. For Free Text Invoices specifically:

Accounts receivable → Setup → Forms → Form setup → General tab

Look for the section that specifies which ER format to use for Free Text Invoices. Select your derived format from the dropdown.

This varies by document type. Each business document (invoice, packing slip, bank statement, etc.) has its own setup location for assigning the ER format. There's no single universal place. The Pattern: go to the module's Form setup or Print management, find the document, and look for an ER format assignment field. For invoices, it's in AR. For purchase orders, it's in AP. For bank statements (inbound), it's in Cash and bank management. Microsoft's docs list the specific paths for each.
Alternative path — Print Management: For most outbound documents, you can also assign ER formats via Print Management (module → Setup → Forms → Form setup → Print Management). Print Management lets you set different formats per customer/vendor, per document type, etc. — more flexible than the global assignment.
Verification: The dropdown shows your custom format name. If it doesn't appear in the dropdown, either: (a) the version isn't Completed (some assignment paths require Completed), or (b) the format's data model type doesn't match what the document expects — you derived from the wrong parent.
Custom format assigned to the business document
2
Run a test document
▸

Create or find an existing business document (e.g. a Free Text Invoice) and print/generate it.

For Free Text Invoices: go to Accounts receivable → Invoices → All free text invoices. Pick one (or create a test one). Click Print → Selected.

F&O will use your assigned ER format to generate the output file. The result is typically a file download (Excel or PDF depending on format settings).

First-run failures: The most common output on first attempt is an error in the infolog. Read it. The two most frequent causes:
1. Binding error: "Cannot evaluate expression..." — a formula references a field that's null or the wrong type. Fix the formula.
2. Template structure error: "Named range X not found" — you renamed/deleted a range in Excel that the format tree still references. Re-sync.
Verification: A file downloads. Open it. Your custom branding/layout appears. Data from the actual invoice populates the fields. Check the line items section — verify it repeats correctly for multi-line invoices.
Output document generated with correct data and layout
3
Configure ER Destinations (optional but recommended)
▸
Organization administration → Electronic reporting → Electronic reporting destination

ER Destinations control where the generated document goes. Options include:

  • Screen: Opens in browser (default for most formats)
  • Email: Auto-sends as attachment — useful for invoice emailing workflows
  • File/Archive: Saves to Azure Blob or SharePoint
  • Printer: Direct to network printer

Click New. Select your format configuration. Then configure destinations per output component.

For testing: Leave the default (Screen). Only configure email/file destinations when you're ready for UAT or production.
Destinations configured (or left as default for testing)
What Goes Wrong and How to Fix It

ER Trace — your diagnostic superweapon

Before debugging anything, turn on ER tracing:

Organization administration → Electronic reporting → Reporting configurations → User parameters (Action Pane) → Turn on "Run in debug mode" / "Trace"

Run the document again. Then go to Configurations → Action Pane → Logs → Execution logs. This gives you a step-by-step trace of every binding evaluation, every data query, and every template write. It's verbose but it tells you exactly where the failure occurred.

!
"Configuration not found" when assigning format
▸

Cause: The format's data model root definition doesn't match what the business document expects. Each document type is hard-coded to look for a specific data model root (e.g. "InvoiceBase").

Fix: You derived from the wrong parent format. Go back to the Global repository, find the correct format for your document type, and derive from that instead.

!
"Template validation failed" on upload
▸

Cause: The uploaded .xlsx has structural differences the format can't reconcile. Often caused by:

  • Editing in LibreOffice/Google Sheets (different internal XML)
  • Saving as .xls instead of .xlsx
  • Breaking a named range by deleting rows/columns it spans
  • Password-protecting the workbook or sheets

Fix: Re-export the original template, redo your edits in desktop Excel, ensure .xlsx format, no protection. Verify named ranges are intact in Name Manager before uploading.

!
Output generates but data is blank/missing
▸

Cause: Binding exists but the data model node is null at runtime. This means the Model Mapping isn't pulling the data.

Fix path:

  1. Enable ER trace and re-run
  2. In the trace, find the binding evaluation for the blank cell
  3. Check if the data model field received a value (it'll show "null" or empty)
  4. If null: the issue is in the Model Mapping. Open the Model Mapping designer, find the datasource for that field, and verify the query/join/filter is correct
  5. Common sub-cause: the model mapping has a filter (e.g. by legal entity) that doesn't match your test data
The classic: You run it in company USMF but the test invoice is in company DAT. ER runs in the context of the current legal entity. Switch companies.
!
Repeating rows only show one row
▸

Cause: The named range in Excel covers only one row (correct for the template — it's the template row). But the format element's Replication property isn't set to the list binding.

Fix: In the format tree, select the repeating element (e.g. "InvoiceLine"). Check its properties — there should be a "Collection" or "Replication" setting bound to the data model's list node. If it's bound to a single record instead of a list, it'll only render once.

!
Format warnings about "shared model configurations"
▸

Cause: Multiple format configurations reference the same data model, and they have different version requirements. This is the noise you saw before on Sepura — it's the ER equivalent of shared dependency warnings.

Fix: Usually ignorable. These are warnings, not errors. They mean: "format A expects model version 50 but format B expects version 52." As long as the model versions are backward-compatible (which Microsoft's almost always are), it works fine. The warnings go away if you rebase all formats to the same model version.

!
Performance — document takes minutes to generate
▸

Cause: ER's data model queries are not optimized by default. Each binding can trigger a database round-trip. A format with 50 bound cells and 200 line items = 10,000 queries if done naively.

Fix:

  • Use ALLITEMS or ALLITEMSQUERY functions to batch-load lists instead of lazy-loading
  • In the Model Mapping, ensure datasources use Join instead of nested lookups where possible
  • Enable ER caching (available in newer versions) for frequently-read reference data
  • Check ER trace for repeated identical queries — that's the smoking gun

Excel Template Rules

RuleDetail
File format.xlsx only. Not .xls, not .xlsm.

Named rangesEvery cell ER should populate must be inside a named range. The range name must match the format tree element name.
Repeating sectionsOne-row named ranges. ER clones the row. Don't merge cells across the range boundary.
